# 生成原理

一句话：把原图缩成 N×N 个格子，每个格子取平均色，再去方块调色板里找**肉眼看起来最接近**的那一块。

听起来简单，效果好坏全在「最接近」这三个字怎么定义。

## 为什么不能直接比 RGB

两个颜色在 RGB 里的欧氏距离，和人的感受不成比例。最典型的例子是绿色：RGB 里差很多的两个绿，
人眼几乎分不出来；而蓝色稍偏一点，人一眼就能看出。

所以匹配分两步：

1. **粗筛**：在 Lab 空间（近似人眼感知的均匀色彩空间）算欧氏距离，从上百个方块里取一小撮候选；
2. **精算**：对候选逐个算 **CIEDE2000** 色差，取最小的那个。

CIEDE2000 是国际照明委员会给出的色差公式，专门处理了感知均匀性问题，也补偿了蓝紫色区域的偏差。
代价是计算量大——直接对 142 个方块逐格算 CIEDE2000，160×160 的画幅就是 360 万次，
所以才有前面的粗筛。

::: tip 为什么值得这么麻烦
像素画的观感主要取决于**色阶是否连续**。用 RGB 距离时，一张人像的肤色过渡经常会突然跳一档，
或者整片偏灰；换成 CIEDE2000 后，同样的方块集合能榨出更细的层次。
:::

## 方块代表什么颜色

每个方块用一个**平均色**参与匹配，而不是贴图里的某一个像素。做法是把 16×16 的原版贴图逐像素平均，
得到代表色，写进 `src/core/blocks.ts`。

贴图本身只用于预览：画布上看到的是真实材质，导出永远是纯色——施工图要的是看得清，不是好看。

::: warning 平均色的局限
带纹理的方块（比如圆石、砖块）平均下来会偏灰。想让画面更「有质感」，可以打开「方块质感」，
它给每格加一圈明暗边，让画布看起来像堆起来的方块。这只影响预览，不改匹配结果。
:::

## 采样：一格等于多少像素

原图先居中裁成正方形（不拉伸变形），再按目标格数分块取样：

- 每块内的像素**按面积加权平均**，不是简单取中心点——否则缩小时会丢掉细节、放大时会漏掉小元素；
- 全透明的格子保留为**空格**，不强行填色，这样 logo 的镂空能留住；
- 半透明像素按 alpha 与原图底色混合后再参与平均。

## 抖动：什么时候开

「颜色抖动」用有序抖动（Bayer 矩阵）在两个最接近的方块之间交替，用噪点换更自然的渐变色带。

它解决的是「方块颜色档位不够」的问题：天空只有三四种蓝，直接匹配会出现生硬的色带，
抖动后能看起来像连续渐变。

但代价很明显——大面积纯色区域会出现可见的棋盘噪点。所以**默认关闭**，并且强度只有常规实现的一半。
什么时候值得开：渐变占比大、且画幅 ≥ 96 的图像。

## 去杂点

去杂点做的是另一件事：如果一个格子与它上下左右四个邻居都不同，但颜色又很接近其中某一个，
就把它并过去。这样能消掉照片噪点造成的零星孤岛，同时保住眼睛和高光这类真正需要对比的地方。

它和抖动是反向操作：抖动主动制造噪点，去杂点主动消除噪点。两个一起开通常没有意义。

## 手画的格子为什么能留住

匹配结果存在一个索引数组里，另外还有一层**手画遮罩**记录哪些格子是用户改过的。
换方案、换画幅、重新生成时，一律先整图重算，再用遮罩把手画过的格子盖回去。

这样既不会出现「换了大方案还是旧结果」的问题，也不会把用户的心血冲掉。
代价是换方案时总要重算一遍——这正是它该做的事。
